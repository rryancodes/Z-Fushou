# ZFushou Live Incident & Topic Tracking Engine (Real-Time Semantic Layer)

## Purpose

Build a new real-time semantic tracking system that operates independently from the existing daily semantic pipeline.

The existing pipeline remains unchanged and continues producing daily topic summaries, clusters, analytics, and embeddings.

This new system is designed to detect, track, evolve, and summarize active discussions, incidents, complaints, emerging issues, and important conversations as they happen.

The goal is not to summarize an entire day.

The goal is to answer:

* What is happening right now?
* What issue is actively being discussed?
* Has the discussion evolved?
* Was the issue resolved?
* Does this require product attention?
* What is the current state of the discussion?

---

# Core Design Principles

## MUST NOT use fixed message counts

Forbidden:

* Analyze every 5 messages
* Analyze every 10 messages
* Analyze every 20 messages

Reason:

Conversation sizes vary dramatically.

A fixed count causes:

* Context loss
* Topic fragmentation
* Artificial boundaries

The system must use semantic drift instead of message count.

---

## MUST start from zero state

At system startup:

```text
No topics
No incidents
No active discussions
```

The first incoming message must be enough to create the first live discussion state.

No historical context is required.

---

## MUST be stateful

Unlike the daily pipeline:

```text
Input
↓
Process
↓
Output
```

The live system maintains active memory.

```text
Message
↓
Update state
↓
Evaluate discussion
↓
Store state
↓
Wait for next message
```

---

# Discussion Routing Layer

Purpose:

Determine ownership.

Not intent.

Not sentiment.

Not classification.

Only:

```text
Product-side issue
User-side issue
Mixed
Unknown
```

Examples:

"API returns 500"

→ Product-side

"My laptop is broken"

→ User-side

"Not sure why login fails"

→ Unknown

This helps prioritization later.

# Rolling TextTiling Layer

This is the heart of the system.

The daily pipeline uses full-day segmentation.

The live engine uses rolling segmentation.

 )

# Boundary Detection

Purpose:

Detect topic shifts.

Not message count.

Not time count.

Semantic shifts.

---

Example

Discussion:

```text
API error
API error
API error
Rate limits
API error
```

No boundary.

---

Discussion:

```text
API error
API error
API error
```

Then:

```text
Can GLM 5 beat Claude?
```

Boundary.

New discussion.

---

Boundary candidate generated when:

```text
Cohesion score drops
AND
Similarity drops
```

Both required.

Never one alone.

---

# Quiet-Time Flush

Some discussions end naturally.

No boundary appears.

No explicit resolution appears.

---

Example:

```text
Login broken
Any fix?
Still broken
```

Then silence.

---

After:

```text
10 minutes
```

Configurable.

Discussion auto-closes.

LLM generates final state.

# Timeline Engine

Every active case maintains a timeline.

Example:

```text

Additional users confirm issue

09:08

09:12

```

Timeline updates only when:

* Significant new information appears
* Resolution appears
* Scope changes

Not every message.

# LLM Usage Rules

LLM must NEVER run on every message.

Too expensive.

Too slow.

Allowed triggers:

2. Boundary closure
3. Quiet-time closure
4. Significant timeline update

Only.
